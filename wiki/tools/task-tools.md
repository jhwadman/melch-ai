# Task tools

One store holds two kinds of record: `todo` (the user's own tasks: open → done | cancelled) and `background` (jobs: queued → running → done | failed, and cancelled before or while they run). The store is a JSON file written atomically, at `MELCHIZEDEK_TASKS_FILE` or `outputs/tasks.json` under the working directory: deployment config, never YAML and never an argument. Every call re-reads it, so the conversation and the worker see each other's writes.

<!-- wiki:generated section="contracts" source="lib/tools/taskTools.ts" -->
| Tool | Arguments | Does |
|---|---|---|
| `task_add` | `title`, `notes?`, `due?` | Add a task to the user's own to-do list: something THEY need to do or remember. |
| `task_queue` | `title`, `instruction` | Queue a background job: work that takes a while (reading several pages, a long draft, a comparison) and should not block the conversation. |
| `task_list` | `status?`, `kind?` | List the user's tasks and background jobs, one line each with id, status, and title. |
| `task_get` | `id` | Read one task or background job in full, including a finished job's result. |
| `task_update` | `id`, `status?`, `title?`, `notes?`, `due?` | Change a task: mark it done, cancel it, reopen it, or edit its title, notes, or due date. |

**The tools never run a job.** A tool that runs agents is the composite the [tool contract](/tools/tool-contracts.md) refuses, so `task_queue` only writes a record, and `scripts/assistant_worker.ts` (`npm run assistant:worker`; `melchizedek-worker` in the package) runs it: it claims the oldest queued job, runs its instruction as a single turn through `runDurableTurn` (`lib/runtime/native/checkpoint.ts`), which calls `runSyndicateTurn` (`lib/runtime/syndicateTurn.ts`) with one agent on a fresh in-process store and the engine's [native loop](/overview/native-loop.md), and writes the result or the error back for `task_get`. The agent defaults to the [Assistant](/agents/assistant.md)'s Worker; `--syndicate <file> --agent <name>` picks any syndicate and agent. A job that runs past ten minutes is aborted and recorded as failed. The worker's log names a job by its id and owner and measures its instruction (`<id> started (<n> chars)`), never prints it; the turn's own lines are the turn runner's, which name tools and never their arguments. Run one worker per store: the claim is a read-modify-write, not a lock.

**A run is durable** ([ADR 0113](/decisions/0113-durable-runs-checkpoint-the-sessions-beside-the-job.md)). At every step boundary (a stored tool response with no call left unanswered) the worker checkpoints the run's sessions beside the job, never inside its record: `<store>.checkpoints.json` next to the JSON file, the `checkpoint` column on Postgres (migration 0014). A job claimed again resumes from its last checkpoint and takes the next step instead of starting over; a dispatch run classifies its route again, and one checkpointed inside an agent route resumes there ([ADR 0121](/decisions/0121-checkpoint-cap-and-dispatch-route-resume.md)). A job left running by a dead worker is re-queued by the next worker to start and, on Postgres, by any worker between polls once its lease runs out, and failed after two interruptions; SIGTERM aborts the step in flight and re-queues the job with its checkpoint. `task_update` may cancel a running job: its claim ends, the worker sees that at its next lease renewal or checkpoint save, aborts the run and writes no result over the cancellation. A checkpoint lives only while its job is running or queued. A checkpoint above the cap, 5 MiB of JSON by default (`MELCHIZEDEK_CHECKPOINT_MAX_BYTES` for the worker, `TaskBackendOptions.checkpointMaxBytes` on `fileTaskBackendWith` and `PostgresStorageOptions.taskQueue`), is not stored: the job keeps its previous checkpoint, the save still reports whether the worker's claim holds, and one line names the job id and the sizes, never the content. The sidecar is written compact.

**Every worker write is bound to one claim** ([ADR 0157](/decisions/0157-job-mutations-are-fenced-by-a-per-claim-token.md)). A worker id names a process and can claim the same job twice, so `claimNext` gives each claim a token, written in the statement that takes the job (`claim_token`, migration 0025, beside `record` and never in it; `task_get`, `task_list`, `read()` and the operator view do not show it, and the worker never logs it). The job the worker holds carries it as `job.claim`. On Postgres, `renew`, `saveCheckpoint`, `finish` and `requeueInterrupted` each match owner, job id, worker id, token, `running` and a lease still in the future, and a job carrying no claim changes nothing.

An expired lease is no longer owned: its worker's next write is refused whether or not `recover` has run. `recover` clears the claim in the statement that requeues or fails the job, and so does every other exit from `running`. `finish` answers `accepted` or `lost`; a lost finish reports no success, writes no record, and leaves the checkpoint alone, which may be the current claim's. A finish racing a recover ends one way: a finish that reaches the row second re-reads it and finds the claim gone, and a recover that reaches it second skips it.

The worker's lease policy (`lib/runtime/claimedJob.ts`): one renewal runs at a time, and the worker trusts only the last window the store confirmed, measured from when that renewal was sent. A renewal that throws is retried inside that window; at its end the claim is over, in flight or not. The run then stops as a **lost claim**, which writes nothing and is distinct from a **graceful stop** (SIGTERM: the job goes back under its claim, or nothing happens if the claim has gone) and from an **ordinary error** (recorded on the job as `failed`). A finish or requeue that throws is retried with the same outcome for at most one lease. A durable run's sink is bound to the claim (`claimCheckpoints`): the checkpoint format has no claim in it, so any earlier checkpoint restores under a new claim. The file store applies the same rule through a token on the running record, stripped from `read()`, without the guarantees: it has no leases and no lock between processes, so it stops a claim already stale from overwriting a newer one and is not a transaction.

`FencedTaskBackend` is the capability: `fencedClaims: true`, `finish` answering a result, and `requeueInterrupted`. Both built-in backends are one, and the worker takes its backend through `requireFencedBackend`, so there is no unfenced path to fall back to. A custom `TaskBackend` written against the earlier shape still type-checks; it cannot run under the built-in worker. Fencing holds only among workers that have it: an earlier release neither writes nor checks the token, so upgrade by applying migration 0025, draining the old workers, then starting the new ones.

Exposure: the default store is one file with no caller identity, so on a shared A2A endpoint every caller would share one list; on that store a syndicate carrying these tools is for one person's machine. With `DATABASE_URL` the server and the worker use Postgres instead (migration 0009): each tool call is filed under its caller's scope key, so every caller has their own list and ids, and any number of workers claim jobs with `FOR UPDATE SKIP LOCKED` under a lease they renew; a job whose worker died is queued again, or failed after two attempts. The view `melchizedek_task_queue` (migration 0018) is the queue as an operator reads it: one row per background job with `owner`, `id`, `title`, `status`, `attempts`, `retries` (attempts beyond the first), `max_attempts`, `dead_lettered` (failed, and not run again unless retried), `last_error`, `lease_owner` and `lease_until`, `has_checkpoint` and `checkpoint_at`, and the job's times; todo items are not in it. It is revoked from the API roles like the table. `postgresStorage().retryTask(owner, id)` is its Retry: `applyRetry`, the same rule as `task_update`'s `queued`, puts a failed or cancelled job back on the queue with its attempts and error cleared, and answers `not-found` or `not-retryable` otherwise. A job result is the worker's output and reaches the Assistant as material to report, never as instructions.
